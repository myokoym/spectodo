# Spectodo v0.2 common-standard decision and compatibility review

Date: 2026-10-12
Status: common target approved in principle; release candidate NOT yet promoted. End-to-end acceptance is tracked in docs/validation-v0.2.md.

## Decision

Once v0.2 is promoted, new repositories and deliberate upgrades use Spectodo Language v0.2 regardless of code presence or scope count. A pre-existing v0.1 inventory is valid until explicitly migrated. This is a central Spectodo policy, not a consumer-specific format decision.

## Review of v0.1 to v0.2

| Dimension | v0.1 | v0.2 stable | Compatibility rule |
|---|---|---|---|
| Root inventory | SPECTODO.md, no Scope | SPECTODO.md containing Scope: PROJECT: . | Legacy file keeps v0.1 semantics; no auto-reparse |
| Multiple inventories | Not standardized | One canonical file per declared scope root | Explicit route required |
| Scope ID | Absent | Unique per repository | Introduce only during migration |
| Shared policy | v0.1 constraints project-wide | Scope-local; separate single shared policy where necessary | Audit every legacy constraint |
| Versions/priorities/axes | Vn, Pn, D/I/P/V | Unchanged | Distinguish language version from target version |
| Optional escaped text | v0.1 rules | v0.2 explicit escapes | Revalidate affected content in migration |
| Agent operation | Root implicit | Explicit routes for new v0.2 | Generate instructions automatically |
| Code-free planning | Ambiguous application wording | Research/design outcomes explicitly supported | I:- only where implementation truly not applicable |

## Proposal gaps resolved

1. Opt-in and single-project v0.1 recommendation conflicted with a universal installer: now v0.2 is stable default for all NEW adopters.
2. Scope mapping had no repeatable generator: kickoff now discovers project boundaries, installs one rooted scope by default, and writes explicit routes without requesting a language version from the project.
3. No-code use was ambiguous: design/research deliverables are first-class verifiable outcomes; absent code never means implementation complete.
4. Repeat runs and update rules were missing: matching by canonical path/ID/statement; no reset, new ID reuse or duplicate requirement on rerun.
5. Migration lacked an execution artifact: migration ledger requires one disposition per constraint, item, version, reference and route; preserve one-to-one status only.
6. Historical documents were prone to promotion into current requirements: kickoff assigns source authority and traces claims and residual uncertainties.
7. Neither reproducible fixtures nor runnable checks accompanied the proposal: optional tests and independent semantic acceptance cases now form the promotion gate.

## Migration and rollback

A v0.1-only repository stays valid. When asked to adopt the current stable common foundation, produce an explicit audited migration: read every existing item/constraint; assign successor or retirement evidence; introduce root Scope; preserve stable IDs, statement and independently evidenced progress; recompute references and routes; verify all canonical paths. A split additionally needs a ledger for every transferred item and shared policy. Preserve the original in Git history, not a second canonical SPECTODO.md copy.

Rollback is another audited migration. Removing the Scope heading or nested inventories alone is forbidden: first reconcile all records, divergent states, and shared policies into one v0.1 root file, then validate v0.1 syntax. New v0.2 features are not implicitly writable by a legacy v0.1 agent.

## Explicitly out of scope

No mandatory parser, backend, renderer, issue tracker, or CLI; no automatic guessing of ambiguous project boundaries or completion evidence; no custom progress axes; no automatic rewriting of unrelated historical research.
