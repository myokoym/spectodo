# 詳細実行計画オプション（低コストモデルへの作業委譲）

Spectodo Language v0.2 stableに追加する、**任意の運用手順**です。言語の構文・スコープの振り分け・優先度・対象バージョン・D/I/P/Vは変更しません。仕様と進捗の唯一の正本は従来どおり `SPECTODO.md` です。

**このガイドを導入先に配布すれば、Spectodo本体のREADMEをコピーしなくても利用できます。** 以下の日本語指定文を作業AIにそのまま渡してください。既定は未完了の採用済み要件全体で、項目IDを毎回指定する必要はありません。特定項目のみ必要な場合だけIDで範囲を限定してください。

## 最短の指定方法（そのままコピー）

**① 未完了作業全体の詳細手順を一括作成（実作業はしない）**

~~~text
Spectodoの詳細実行計画オプションで、このリポジトリの採用済み・未完了Requirement全件について、依存関係に沿う詳細手順を一括作成・更新してください。
全Scope・対象VersionのIDを棚卸しし、docs/spectodo-execution/README.mdに
「対象ID→作業単位・実行順序・検証・blocked理由」を網羅的に記録してください。
関連項目は作業単位にまとめ、各手順に対象ファイル・前提・具体操作・期待結果・
検証・失敗時の停止/復旧条件・再開位置を示してください。
不明点は該当単位だけblockedにし、独立して計画できる範囲は続けてください。
計画を自己点検し、今回は実装・デプロイなどの実作業を開始しないでください。
~~~

**② 作成済みの全体計画に従って連続実行する**

~~~text
Spectodoの詳細実行計画に従って、docs/spectodo-execution/README.mdに記録された
実行可能な作業単位を依存順に連続して実行してください。
各単位の着手前に現状・前提・既存変更を照合し、手順に従って検証してください。
検証済みの結果だけを記録し、対応するSPECTODO.mdのD/I/P/Vをその都度整合させてください。
項目や計画ファイルごとに確認待ちせず、次の安全な単位へ進んでください。
不明な設計判断、必要な権限、不可逆操作、テスト失敗は該当単位をblockedにして
理由と再開条件を残し、影響しない作業は継続してください。
計画索引がない、対象scopeを特定できない、依存関係に矛盾がある場合は、
推測で作業せず未解決事項と実行可能な範囲を報告してください。
~~~

※詳細実行計画オプションは明示要求時だけ有効です。古い固定SHAのSkill・ガイドには追加されないため、必要なら共通基盤を明示更新してください。

## 1. 使う条件と責任の所在

- **初期状態では無効です。** 通常のキックオフ・仕様一覧の更新・監査では、詳細実行計画を自動生成しません。[共通導入ガイドの詳細実行計画付きの完全な指定文](https://github.com/myokoym/spectodo/blob/main/docs/adoption.md#詳細実行計画付き新規導入の指定方法そのままコピー)を選んだ場合にのみ、資料再編とinventory整備後、採用済み未完了Requirement全件をカバーする依存順の計画を一括作成します。実装は開始しません。未決事項は関連する作業だけblockedにし、他の計画作成を続けます。すでに作成が許可された計画は、続きを求められたときに再開できます。
- 低コストモデルへの委譲、具体的な実行手順、作業の引き継ぎなどが**明示的に依頼された場合**、指定されたスコープ・項目に限って使用します。共通導入ガイドの詳細実行計画付き新規導入の完全な指示文を使った場合は、その指示文が明示依頼に該当します。標準キックオフそのものは詳細計画作成の依頼ではありません。その指示だけで、無関係な機能の実装や未承認の設計変更まで許可されたことにはなりません。
- 有効な `AGENTS.md` による振り分けで正本の仕様一覧を特定します。ユーザーが文中で示したファイル名だけでスコープを切り替えません。実際の作業前に指示・制約・仕様・関連ファイル・テスト・根拠を確認します。
- 計画作成側は、確定済みの設計判断とその根拠を整理してから委譲します。実行側は不足している要件・コマンド・規則・検証結果を推測で埋めません。
- 計画は**補助文書**です。2つ目の `SPECTODO.md`、新たな仕様正本、別の進捗管理台帳、独自の進捗軸を作りません。専用画面・CLI・サービスも不要です。

## 2. 保存場所と識別方法

全体計画の入口は `docs/spectodo-execution/README.md` です。全canonical scopeと対象Versionに含まれる未完了Requirement IDを列挙し、それぞれ作業単位の詳細計画・blocked・完了済み・対象外（理由付き）のいずれかに対応付けます。作業単位の依存、順序、並行可能な枝、検証の節目、次の実行候補と再開条件をこの入口から追えるようにします。これは補助計画の索引であり、第二のSpectodo inventoryではありません。

関連Requirementを依存・変更範囲・検証境界で適切にまとめて `docs/spectodo-execution/<スコープID>/<安定した作業単位名>.md` に保存します。**1項目1ファイルや1項目ごとの利用者確認を必須にしません。** ただし明示的に特定IDのみの計画が要求された場合は従来の `<項目ID>.md` を使用できます。

特定IDを明示指定した小規模計画の例は `docs/spectodo-execution/PROJECT/APP-001.md` です。標準の一括計画では上記の作業単位名を使い、各計画に関係する正本IDをすべて記載します。

- 依存・作業対象・検証内容が共通する項目は作業単位に集約し、対象IDをすべて列挙します。別々に検証できる作業まで無理にまとめず、同じ仕事の計画を重複作成しません。
- 既存の有用な文書やパスと衝突する場合だけ、適切な別の補助文書パスを使います。
- 判明していれば現在のブランチ、コミット、参照元ファイルや内容の識別情報を記録します。Git管理外・企画資料のみの場合は未確認と明記し、架空のSHAを記載しません。導入済みの配布元Spectodo固定SHAも必要に応じて記録します。
- 発見しやすくなる場合だけ正本の該当項目に計画への `@ref` を追加し、既存の参照を維持します。計画の手順やチェック欄を仕様一覧の1行へ転記しません。新しいスコープは作りません。

## 3. 計画に必要な内容

1. **対象と目的：** スコープIDと場所、正本ファイル、作業単位がカバーする全項目ID、製品の対象バージョン、完了させる結果、対象外、依存・先行作業、根拠となる仕様と承認済みの判断。
2. **着手前の状態：** ブランチ・コミット・作業ツリーの変更有無、関連ファイル、前提条件、必要な依存関係・環境、未確認事項。企画のみのプロジェクトにコードがあると仮定しません。
3. **順番に実行できる手順：** 各手順に、前提、変更・確認する具体的なパス、操作内容、観測できる期待結果、確認方法（コマンドまたは人手での照合）、失敗時の行動を記載します。コマンドは対象環境で使えることを確認してから記載し、作業ディレクトリやOSの条件も必要に応じて明記します。
4. **合格条件と復旧方法：** 元の仕様文と対応する確認事項、合否判定、維持すべきテスト、既存変更を壊さない条件、やり直し・差し戻しの範囲、推測せず相談する条件。
5. **中断・引き継ぎ：** 最後に確認できた手順、実測した証拠と成果物、次の未着手手順、停止理由、計画後の変更、最終的に照合すべきD/I/P/Vの状態。計画側のチェックは正本の進捗より優先されません。

「機能を実装する」「十分にテストする」だけでは、委譲可能な手順として不十分です。まだ確認できない内容を仮定して架空のパッチ・期待出力・完了条件を作らず、まず範囲を限定した調査を行う手順と停止条件を設けます。

## 4. 計画の作成手順

1. **全体棚卸し：** 明示された全スコープの正本と採用済みの対象Versionを調べ、未完了Requirement IDを一件ずつcoverageへ記録します。完了・未採用proposal・blockedを区別し、同じ作業単位にまとめるIDと依存関係を特定します。
2. **手順の粒度と実行順：** 作業単位とその依存順、同時に進められる枝、先行条件を定義します。各単位は設計判断の境目、独立して検証できる変更、危険な操作を基準に分割します。単純なコマンドまで過度に細分化しません。
3. **事前確認：** 未決定事項、認証情報、権限、環境不足、既存の未コミット変更、破壊的操作を特定します。承認されていない不可逆な判断は勝手に行いません。
4. **文書化：** 全体索引の全ID coverageと各単位の依存・実行順を先に記録し、[記入例](../examples/execution-plan.md)の構造に沿って単位ごとの手順を書きます。架空のパスを実際に確認したパスに置き換え、選択肢があれば観測結果に応じた分岐を明記します。
5. **自己点検：** 未完了IDのcoverage漏れ・重複、依存関係の循環、ファイルの存在（新規作成の場合はその明記）、手順順序、残る設計判断、別の会話でも再現できるか、仕様ごとの検証、復旧方法、中断後の再開方法を別の視点から点検します。問題が見つかれば修正し、影響範囲を再確認します。
6. **引き継ぎ：** 全体索引へのパス、最初に実行可能な作業単位、依存順の次候補、blockedと解除条件を伝えます。実行側に現在の指示・前提を確認させますが、単位ごとに依頼し直させません。

## 5. 実行・停止・計画更新

一括計画の実行依頼では `docs/spectodo-execution/README.md` の依存順に**連続して**進みます。各安全な作業単位の合格後は関連RequirementのD/I/P/Vを根拠に照合し、そのまま次の実行可能な単位へ進みます。ID境界・計画ファイル境界・Priority同値は確認待ちの理由ではありません。未決定の設計、必要な承認、失敗した必須テスト、不可逆操作などで止まるのは影響を受ける単位と従属する枝だけです。安全で独立した別の枝があれば継続します。すべての作業がblocked、または利用者の意思決定を要する場合に理由と再開条件を報告します。**作成のみ依頼された場合は、ここに書いた実行を開始しません。**

- 各手順の前に、前提条件と関連資料の内容が計画時から変わっていないか確かめます。無関係なコミットだけで失効とはしませんが、対象ファイル・要件・スコープ・指示・合格条件・ユーザーの変更に影響がある場合は差分を評価します。
- 実行可能な次の手順だけを進め、確認できた結果と根拠を記録します。部分的にしかできなかった手順や未検証の手順を完了にしません。
- ファイルの欠落、規則の衝突、承認のない判断、想定外の差分、権限・コマンド不足、復旧手順外のテスト失敗、危険な操作が発生したら、**推測で進まず停止して報告**します。対象パス、観測事実、失敗した確認方法を示します。
- 再開時は計画、正本、作業ツリーの差分、最後の証拠を再確認します。変更された前提の影響を調べ、破壊的手順を無条件に再実行せず、進捗も勝手にリセットしません。
- 実際の作業で状態が変わったら、証拠に基づいて正本の該当D/I/P/Vだけを更新し、チェック欄を整合させます。計画の手順をチェックしただけでは `I:x` や `V:x` の根拠になりません。
- 情報が変わった場合は必要な手順のみ修正し、確定済みの成果・ID・経緯を残します。同じ入力で計画を作り直しても、根拠のない新規作業や無意味な差分が増えない状態を目指します。

## 6. 実モデル・費用対効果の検証（未実施）

ガイドやテストが整っていることは、低コストモデルで実際に作業できることや費用削減の証明ではありません。効果を主張する前に、**企画のみ／コードとテストあり／途中中断・入力変更からの再開**という条件で実タスクを実行し、計画あり・なしを、事前に決めた同じ合格基準で比較します。

モデル名と版、料金基準、トークン・ツール使用量、計画の作成・実行・保守費、再試行、人間による介入、経過時間、成功した検証、回帰、不明な問題を記録します。実行だけでなく**計画作成やレビューを含む総費用**を比較し、計画を作った方が高くついた例も報告します。正確性を先に評価し、そのうえで費用を判断します。
